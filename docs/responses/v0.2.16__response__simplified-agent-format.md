## 1. Technical Feasibility Assessment

### Verdict: Feasible, with boundary conditions that require deliberate design choices

The brief proposes a second on-disk format (`.issues` flat files) that compiles down to the existing in-memory graph representation. This is architecturally sound because the core insight -- **the on-disk format does not need to mirror the in-memory format** -- respects the existing separation between storage and graph model. The Memory-FS abstraction layer already decouples storage backends from the graph domain. Adding a new *input format* is a narrower change than adding a new storage backend; it sits above storage, in the parsing/loading pipeline.

**What exists today and supports this proposal:**

| Component | Current State | Relevance |
|-----------|--------------|-----------|
| `Graph__Repository` | Loads `issue.json` files from `data/{node_type}/{label}/` paths via Memory-FS | The `.issues` parser bypasses this path-based loading; it creates `Schema__Node` instances directly |
| `Node__Service` | Business logic for CRUD; generates labels like `Bug-27` from type + sequential index | The parser must either use this service (respecting index management) or produce pre-formed nodes that skip it |
| `MGraph__Issues__Domain` | In-memory graph with nodes, edges, and indexes (`index_by_label`, `index_by_path`, `index_by_parent`) | The parser's output must be compatible with this domain layer |
| `Schema__Node` | 14-field Type_Safe class (node_id, node_type, node_index, label, title, description, status, timestamps, tags, links, properties) | The parser must map 3 flat-file fields (label, status, description) to this 14-field schema, filling defaults for the remaining 11 |
| `Safe_Str__Node_Label` | Regex: `^[A-Z][a-zA-Z]*(-[A-Z][a-zA-Z]*)*-\d{1,5}$` (e.g., `Bug-27`, `User-Story-3`) | The brief's proposed labels (`enable-cloudfront-logs`) do **not** match this regex. This is the single largest compatibility friction point. |
| `Safe_Str__Status` | Regex: `^[a-z][a-z0-9-]*$` | The brief's proposed statuses (`todo`, `in-progress`, `blocked`, `done`) conform to this regex. No issue here. |
| `Safe_Str__Node_Type` | Regex: `^[a-z][a-z0-9-]*$` | The brief's proposed types (`epic`, `bug`, `question`) conform. No issue. |

**Feasibility by feature:**

| Feature | Feasibility | Notes |
|---------|-------------|-------|
| Line-per-issue parsing | Straightforward | Text parsing with pipe delimiter |
| Tab indentation hierarchy | Straightforward | Standard indentation parsing, well-understood |
| Issue type prefix `[bug]` | Straightforward | Regex extraction before the label |
| Cross-reference `-> label` | Moderate | Requires label resolution across files; ordering matters |
| Merge with JSON issues | Moderate | Requires label uniqueness enforcement across both formats |
| Status mapping | Straightforward | Brief's statuses already comply with `Safe_Str__Status` |
| Label format | **Requires architectural decision** | See Section 4 below |

## 2. How the Parser Fits Into the Existing Architecture

### Current Loading Pipeline

Today, when Issues-FS loads a database, the path is:

```
Storage Backend (Memory-FS)
    |
    v
Graph__Repository.nodes_list_all()     -- scans for issue.json files
    |
    v
Graph__Repository.node_load_by_path()  -- reads JSON, returns Schema__Node
    |
    v
Node__Service / MGraph__Issues__Domain -- business logic and graph operations
```

The discovery mechanism is `nodes_list_all()`, which scans all `Storage_FS.files__paths()` for files ending in `/issue.json`. This is hardcoded to the JSON file structure.

### Proposed Parser Placement

The `.issues` parser introduces a **parallel loading path** that sits alongside -- not replacing -- the JSON loader:

```
                        ┌─────────────────────────────────┐
                        │    Database Loader (new)         │
                        │    orchestrates both formats     │
                        └──────────┬──────────────────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    │                             │
                    v                             v
        ┌───────────────────┐         ┌───────────────────┐
        │  JSON Loader       │         │  .issues Parser    │
        │  (existing path)   │         │  (new component)   │
        │  Graph__Repository │         │  Parser__Issues    │
        └────────┬──────────┘         └────────┬──────────┘
                 │                             │
                 │    List[Schema__Node]        │    List[Schema__Node]
                 │    List[Schema__Node__Link]  │    + inferred edges
                 │                             │
                 └──────────────┬──────────────┘
                                │
                                v
                    ┌───────────────────────┐
                    │  MGraph__Issues__Domain │
                    │  (unified graph)        │
                    └───────────────────────┘
```

### Boundary Definition

The parser is a **new component within `Issues-FS` (core library)**, not a new repository. It sits in the loading pipeline between raw file content and the graph domain layer. Its boundary:

| Aspect | Definition |
|--------|-----------|
| **Owns** | Parsing `.issues` file format into structured intermediate representations; inferring issue types, hierarchy, and cross-references from text |
| **Does not own** | Storage access (delegates to Memory-FS), graph operations (delegates to `MGraph__Issues__Domain`), node creation business logic (delegates to `Node__Service` or produces `Schema__Node` directly), CLI command registration |
| **Input** | Raw text content of `.issues` files (obtained via `Storage_FS.file__str()`) |
| **Output** | A list of parsed issue records (intermediate representation) that can be converted to `Schema__Node` instances and edge definitions |

### Recommended Module Placement

```
issues_fs/
    issues/
        loading/                          <-- new package
            Parser__Issues__File.py       <-- single-file parser
            Parser__Issues__Line.py       <-- line-level parsing
            Loader__Issues__Database.py   <-- orchestrates JSON + .issues loading
            Schema__Parsed__Issue.py      <-- intermediate representation (parsed but not yet Schema__Node)
```

This placement keeps the parser within `issues_fs.issues` (the issues subsystem) while separating it from `graph_services` (which handles CRUD on the already-loaded graph) and `storage` (which handles path generation and file access).

## 3. API Design Considerations

### 3.1 Internal API: The Parser

The parser should expose a clean contract that the loader can consume:

```
class Parser__Issues__File(Type_Safe):
    """Parses a single .issues file into structured issue records."""

    def parse(self, content: str, source_file: str) -> Schema__Parsed__File:
        """Parse file content into a structured result."""
        ...
```

Where `Schema__Parsed__File` contains:

```
class Schema__Parsed__File(Type_Safe):
    source_file : Safe_Str__File__Path         # which .issues file this came from
    issues      : List[Schema__Parsed__Issue]   # parsed issues
    errors      : List[Schema__Parse__Error]    # parse errors (line number, message)
```

And the intermediate issue representation:

```
class Schema__Parsed__Issue(Type_Safe):
    label         : str                         # raw label from the file (not yet Safe_Str__Node_Label)
    status        : str                         # raw status
    description   : str                         # raw description
    issue_type    : str                         # inferred or explicit type (e.g., "task", "bug")
    indent_level  : int                         # 0 = top-level, 1 = child, 2 = grandchild
    parent_label  : str                         # label of the parent (from indentation), or empty
    cross_refs    : List[str]                   # labels referenced via -> syntax
    line_number   : int                         # source line for error reporting
```

**Key design choice:** The parser produces an **intermediate representation**, not `Schema__Node` instances directly. This separation matters because:

1. The parser should not need to generate `Node_Id` (UUIDs), `Timestamp_Now`, or `node_index` values -- those are concerns of the node creation pipeline.
2. Validation (duplicate labels, broken cross-refs) happens after parsing, before node creation.
3. The intermediate representation preserves source location information for error reporting.

### 3.2 Internal API: The Database Loader

The loader orchestrates the full pipeline:

```
class Loader__Issues__Database(Type_Safe):
    """Loads a complete Issues-FS database from both JSON and .issues formats."""

    repository     : Graph__Repository
    node_service   : Node__Service
    issues_parser  : Parser__Issues__File

    def load_all(self) -> Schema__Load__Result:
        """Load JSON issues + .issues files into the graph."""
        ...

    def load_issues_files(self) -> Schema__Load__Result:
        """Load only .issues files (for incremental updates)."""
        ...

    def discover_issues_files(self) -> List[str]:
        """Find all .issues files in the storage."""
        ...
```

### 3.3 CLI API: The Check Command

The brief proposes `issues-fs check` (or `verify`). This should be a CLI command in `Issues-FS__CLI` that calls the loader with a validation-only mode:

```bash
issues-fs check                  # validate all files, report errors and summary
issues-fs check --file foo.issues  # validate a single file
issues-fs check --verbose          # include per-issue details
```

The check command does **not** mutate storage. It parses, validates, and reports. Internally, it calls the loader in a dry-run mode that builds the graph in memory but does not persist anything.

### 3.4 CLI API: The Normalise Command

```bash
issues-fs normalise              # convert .issues files to JSON structure
issues-fs normalise --dry-run    # show what would be created without writing
issues-fs normalise --file foo.issues  # normalise a single file
```

This command reads `.issues` files, builds the graph, and writes out the traditional `data/{type}/{label}/issue.json` structure. The original `.issues` files can optionally be removed or kept.

## 4. Data Model Implications

### 4.1 The Label Problem (Critical Decision Required)

This is the most significant architectural tension in the proposal. The existing `Safe_Str__Node_Label` type enforces this regex:

```python
regex = re.compile(r'^[A-Z][a-zA-Z]*(-[A-Z][a-zA-Z]*)*-\d{1,5}$')
```

This allows labels like `Bug-27`, `Task-15`, `User-Story-3`, `Git-Repo-1`. It does **not** allow the brief's proposed labels like `enable-cloudfront-logs`, `dpo-review`, `dashboard-traffic`.

The brief's labels are **semantic slugs** -- human-readable identifiers that describe the issue content. The existing labels are **type-indexed identifiers** -- machine-generated labels that encode the issue type and a sequential number.

**Options:**

| Option | Description | Impact |
|--------|-------------|--------|
| **A: Relax the label regex** | Change `Safe_Str__Node_Label` to accept both formats (e.g., `^[A-Za-z][a-zA-Z0-9-]*(-[a-zA-Z0-9-]+)*$`) | Affects every component that uses `Safe_Str__Node_Label`. The label no longer reliably encodes the issue type, so `parse_label_to_type()` in `Node__Service` and `Link__Service.parse_label()` would need fallback logic. Existing labels remain valid. |
| **B: Use a separate identifier** | Keep `Safe_Str__Node_Label` as-is. Introduce a new field `slug` (or `alias`) on `Schema__Node`. The `.issues` parser maps its label to the slug; the system generates a proper `Safe_Str__Node_Label` (e.g., `Task-42`) internally. Cross-references in `.issues` files use slugs. | Clean separation. No existing code changes. But: agents see slugs in `.issues` files and generated labels in JSON/API output -- two identifiers for the same issue. Resolution logic needed for cross-refs (slug lookup). |
| **C: Two-pass label mapping** | The parser assigns temporary labels during parse, then the loader replaces them with generated `Safe_Str__Node_Label` values and builds a mapping table (slug -> label). Cross-references use the mapping table. | Preserves the existing label contract. But: `.issues` files become write-only -- you cannot read back the generated labels. The diff advantage is partially lost because the on-disk slug does not match the in-graph label. |

**Architect Recommendation: Option B (slug/alias field)**

Option A is tempting for simplicity but weakens a fundamental type contract. The `Safe_Str__Node_Label` regex is used throughout the codebase for type inference (`Bug-27` -> type `bug`). Relaxing it would propagate uncertainty into `Node__Service.parse_label_to_type()`, `Link__Service.parse_label()`, `Path__Handler__Graph_Node.path_for_issue_json()` (which uses the label in file paths), and `MGraph__Issues__Domain.index_by_label`. The cost of that propagation exceeds the cost of a new field.

Option B adds a `slug` field to `Schema__Node` that serves as a human-friendly alias. The `.issues` parser uses slugs. The graph uses proper labels. A bidirectional index (`slug <-> node_id`) enables resolution. The generated label (e.g., `Task-42`) still serves as the canonical identifier in the JSON format, the API, and the graph. The slug is an additional lookup key, like `index_by_path` is today.

However, this decision has enough downstream impact to warrant a full ADR. The options above should be formally evaluated by the team before Phase 1 implementation begins.

### 4.2 Mapping Flat File Fields to Schema__Node

The `.issues` format provides 3 fields. `Schema__Node` has 14. The mapping:

| Schema__Node Field | Source | Strategy |
|-------------------|--------|----------|
| `node_id` | Generated | `Obj_Id()` at load time |
| `node_type` | Inferred from `[type]` prefix, or defaulted from context | Parser logic |
| `node_index` | Generated | Sequential per-type, managed by `Node__Service` or loader |
| `label` | Generated | From `node_type` + `node_index` (e.g., `Task-42`) |
| `title` | `.issues` description field | Direct mapping (description serves as both title and description for the simple format) |
| `description` | `.issues` description field | Same as title, or empty if we treat description as optional detail |
| `status` | `.issues` status field | Direct mapping; already compliant with `Safe_Str__Status` |
| `created_at` | Generated | `Timestamp_Now()` at first load |
| `updated_at` | Generated | `Timestamp_Now()` at load |
| `created_by` | Unknown | Default `Obj_Id()` (placeholder) |
| `tags` | Not provided | Empty list `[]` |
| `links` | Inferred from indentation + `->` syntax | Parent-child via indentation; cross-refs via `->` |
| `properties` | Not provided | Empty dict `{}` |
| `slug` (new) | `.issues` label field | The human-readable slug from the flat file |

### 4.3 Edge/Link Type Mapping

The brief proposes that indentation implies `has-task` (or a default child link type). This maps to the existing `Schema__Link__Type` system, which defines verbs, inverse verbs, and valid source/target type constraints.

| Flat File Pattern | Inferred Link Type | Existing Support |
|-------------------|--------------------|-----------------|
| Tab indentation (parent -> child) | `has-task` / `task-of` (or configurable default) | `Schema__Link__Type` with `verb` and `inverse_verb` exists. The specific verb needs to be registered in `config/link-types.json`. |
| `-> label` syntax | `depends-on` / `depended-on-by` (or `relates-to` / `related-to`) | Same mechanism. The default verb for `->` should be configurable. |
| `[answer]` under `[question]` | `answers` / `answered-by` (type-specific inference) | Would require type-specific link inference rules. Scope for Phase 2 or 3. |

### 4.4 Idempotency Concern

A critical design question: **what happens when the same `.issues` file is loaded twice?**

If the loader generates new `Node_Id` values on each load, the graph will have duplicate nodes after a reload. The system must detect that an issue from a `.issues` file already exists in the graph and update it rather than creating a duplicate.

The slug (or source file + line number) serves as the stable identity for `.issues`-sourced nodes. On reload:

1. If a node with this slug already exists in the graph, update its status and description from the `.issues` file.
2. If no node with this slug exists, create a new one.
3. If a node existed previously but is no longer in the `.issues` file, either mark it as removed or leave it (configurable behavior).

This idempotency requirement further supports Option B (slug field), because the slug becomes the stable external identifier that survives across reloads.

## 5. Risks and Open Questions

### 5.1 Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| **Label format incompatibility** | High | Resolve via ADR before Phase 1. Either Option A, B, or C from Section 4.1. Do not start implementation without this decision. |
| **Cross-file reference resolution** | Medium | Labels/slugs must be globally unique across all `.issues` files and JSON issues. Enforce at validation time. The `check` command must catch duplicates. |
| **Idempotent reload** | Medium | Design the slug-based identity resolution before implementation. Test extensively with reload scenarios: add issue, remove issue, change status, reorder lines, rename slug. |
| **Loss of information on normalise** | Low | When converting `.issues` to JSON, the slug must be preserved. When converting JSON back to `.issues`, the mapping may be lossy (14 fields -> 3 fields). Document this asymmetry. |
| **Tab vs. spaces** | Low | The brief specifies tab indentation. In practice, agents and editors may use spaces. The parser should accept both (with configurable preference) or normalise on save. Recommend: accept both, treat N spaces as one level (configurable N, default 4). |
| **Encoding and special characters in descriptions** | Low | Pipe characters in descriptions will break the parser. Define an escape convention (e.g., `\|`) or use the first two pipes as delimiters and treat everything after the second pipe as description (including any further pipes). Recommend: everything after the second `|` is description. |
| **Performance at scale** | Low | Parsing text files is fast. The bottleneck is the same as today: building the in-memory graph. For databases with thousands of issues across many `.issues` files, the sequential file scan may need optimisation. Not a Phase 1 concern. |

### 5.2 Open Questions

1. **Should `.issues` files be read-only or read-write?** The brief implies agents edit them directly. But if the system also writes to them (e.g., updating status after an API call), we have a two-way sync problem. **Recommendation:** Phase 1 treats `.issues` files as read-only input. The system never writes back to them. Agents edit them directly. Status updates via the API or CLI go to the JSON format. This avoids the write-back complexity entirely. Revisit in a later phase if needed.

2. **Where do `.issues` files live relative to `.issues/` (the traditional directory)?** The brief shows them at the database root alongside `.issues-fs/`. Clarify: are `.issues` files *inside* or *outside* the Memory-FS managed tree? If inside, they need to be excluded from `nodes_list_all()` scanning (which looks for `issue.json`). If outside, the loader needs a separate file discovery path. **Recommendation:** `.issues` files live at the repository root (outside the `.issues/` or `data/` managed tree). The loader scans for them via `Storage_FS.files__paths()` filtered by `.issues` extension.

3. **How does the slug interact with the existing `index_by_label` in `MGraph__Issues__Domain`?** Adding a new index (`index_by_slug`) is straightforward -- the domain layer already has `index_by_label` and `index_by_path`. Adding `index_by_slug` follows the same pattern.

4. **Should the parser be strict or lenient?** The brief mentions freeform input and the need for `issues-fs check`. This suggests a lenient parser that collects errors but continues parsing (rather than failing on the first error). **Recommendation:** Parse all lines, collect all errors, report them together. Individual malformed lines should not prevent the rest of the file from loading.

5. **What is the source of truth for status?** If an agent changes a status in the `.issues` file, and someone else changes the same issue's status via the API (which writes to JSON), which wins? **Recommendation:** The `.issues` file wins at load time (it is the most recent agent intent). But this is another reason to treat `.issues` as read-only in Phase 1 -- avoid the conflict entirely.

6. **How do `.issues` files interact with the fractal/hierarchical issue structure?** The existing system supports issues nested inside other issues via subdirectories. If a `.issues` file is placed inside a subdirectory that represents a parent issue, should its issues be automatically scoped to that parent? **Recommendation:** Defer this for Phase 1. File placement in subdirectories does not automatically imply scoping. Only explicit indentation within the file creates parent-child links.

## 6. Recommended Approach for Phase 1 (Parser)

### 6.1 Prerequisite: ADR on Label Format

Before any code is written, the team needs a decision on how `.issues` labels map to `Safe_Str__Node_Label`. This is the blocking architectural question. The Architect recommends Option B (slug/alias field) but this warrants a formal ADR with input from Dev (implementation cost), QA (testing implications), and the human stakeholder (whether the two-identifier model is acceptable for agent UX).

**Proposed ADR title:** "ADR: Slug-Based Identity for Simplified Issue Format"

### 6.2 Phase 1 Scope

Assuming the label ADR is resolved, Phase 1 should deliver:

| Deliverable | Description |
|-------------|-------------|
| `Parser__Issues__Line` | Parses a single line: extracts label, status, description, optional type prefix, optional cross-refs. Handles the `|` delimiter, `[type]` prefix, and `->` syntax. |
| `Parser__Issues__File` | Parses a complete `.issues` file: handles indentation for hierarchy, calls `Parser__Issues__Line` for each line, builds the list of `Schema__Parsed__Issue` with parent-child relationships. |
| `Schema__Parsed__Issue` | Type_Safe intermediate representation. Not a `Schema__Node` -- that conversion happens in the loader. |
| `Schema__Parsed__File` | Type_Safe container for parse results (issues + errors). |
| `Schema__Parse__Error` | Type_Safe error record (line number, raw line, error message). |
| Unit tests | 100% coverage of the parser. Test cases for: valid lines, empty lines, comment lines (lines starting with `#`), malformed lines, indentation levels, type prefix extraction, cross-reference extraction, pipe-in-description handling, tab and space indentation. |

### 6.3 Phase 1 Explicitly Excludes

- No `Schema__Node` creation (that is the loader, Phase 2 territory or late Phase 1)
- No storage writes (parser is read-only)
- No CLI integration (the `check` command comes in Phase 2)
- No cross-file resolution (single-file parsing only)
- No JSON merge (single-format parsing only)

### 6.4 Phase 1 Design Constraints

1. **Type_Safe throughout.** All classes inherit from `Type_Safe`. All string fields that cross the parser boundary use `Safe_Str` primitives or plain `str` where validation is deferred (the raw label from a `.issues` file is not yet a `Safe_Str__Node_Label`).

2. **No side effects.** The parser is a pure function from text input to structured output. It does not read files (the caller reads and passes content), does not write files, does not modify the graph.

3. **Error accumulation.** The parser never raises exceptions for format errors. It collects `Schema__Parse__Error` instances and returns them alongside successfully parsed issues.

4. **Comment support.** Lines starting with `#` are treated as comments and skipped. Empty lines are skipped. This is not in the brief but is a natural convention for text-based formats and agents will expect it.

5. **Pipe handling.** The description field may contain `|` characters. The parser splits on the **first two** `|` characters only. Everything after the second `|` is the description.

6. **Indentation.** Accept both tabs and spaces. One tab = one level. For spaces, use a configurable threshold (default: 4 spaces = one level, or detect from the first indented line). Mixed tabs and spaces within a file should generate a warning.

### 6.5 Implementation Sequence

1. Define `Schema__Parsed__Issue`, `Schema__Parse__Error`, `Schema__Parsed__File` (schema layer)
2. Implement `Parser__Issues__Line` (single line parsing)
3. Write tests for `Parser__Issues__Line` (all edge cases)
4. Implement `Parser__Issues__File` (file-level parsing with indentation)
5. Write tests for `Parser__Issues__File` (hierarchy, multi-line, comments)
6. Code review by Architect for contract conformance
7. QA review for edge case coverage

### 6.6 Acceptance Criteria for Phase 1

The parser is complete when:

- Given the example file from the brief (`workstream-observability.issues`), it produces 10 `Schema__Parsed__Issue` records with correct labels, statuses, and descriptions.
- Given the hierarchical example from the brief, it correctly assigns `indent_level` and `parent_label` for all nested issues.
- Given lines with `[type]` prefixes, it extracts the issue type.
- Given lines with `-> target` cross-references, it extracts the target labels.
- Given malformed lines, it produces `Schema__Parse__Error` records with accurate line numbers and error messages.
- All tests pass. No test requires network access, file system access, or any Issues-FS service to be running.

## Summary

The proposal is architecturally sound and aligns with the core design principle that storage format and in-memory representation are independent concerns. The primary risk is the label format incompatibility, which requires a formal ADR before implementation begins. Phase 1 (parser only, no integration) is low-risk and can proceed in parallel with the ADR process, provided the parser outputs an intermediate representation that defers label generation.

The recommended implementation order is:

1. **ADR on slug/label strategy** (Architect, blocks Phase 1 integration but not parser implementation)
2. **Phase 1: Parser** (Dev, scoped to pure text parsing, no graph integration)
3. **Phase 2: Loader + Check command** (Dev, integrates parser with Graph__Repository and MGraph__Issues__Domain)
4. **Phase 3: Schema management** (Dev + Architect for schema evolution design)
5. **Phase 4: Normalise command** (Dev)
6. **Phase 5: Agent workflow documentation** (Librarian)

The Architect will produce the slug/label ADR as a follow-up Decision issue.
